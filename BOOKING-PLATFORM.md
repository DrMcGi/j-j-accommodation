# Booking platform setup and handoff

The booking system uses Supabase for Postgres and customer authentication, Ozow One API for hosted payments, and Resend for email. Online booking is intentionally unavailable until each provider is configured. The site does not pretend an unpersisted request was saved or a browser return means a payment succeeded.

## Inventory and rates

The migration seeds 9 bachelor units and 4 two-bedroom units, both available for overnight and monthly stays. Each physical room is shared inventory across both stay periods. An exclusion constraint prevents an active payment hold or confirmed booking from overlapping another booking of the same unit. Availability blocks are serialized against unit assignments and cannot be added across a confirmed stay.

The monthly amounts are the current advertised rates: R7,500 bachelor and R13,500 two-bedroom. The current site advertises overnight at R850 per night. The admin approves every request, assigns an actual unit and enters the final charge before the room is held for payment. Confirm whether the overnight price is per room or per bed and whether the listed monthly price applies to partial months before automating rate calculations. The admin must also confirm the occupancy limit of the assigned unit while preparing its agreement; the booking request's general input limit is not a representation of physical room capacity.

## Providers

1. Use a separate Supabase staging project before production. Local development credentials belong in the ignored `.env.local`; deployment credentials belong in the hosting provider's secret settings. Never commit environment files.
2. Apply `supabase/migrations/202611130001_booking_platform.sql` to staging. In the Supabase dashboard, open the correct project, choose **SQL Editor → New query**, paste the complete contents of that migration file, and click **Run**. Check that the query succeeds before proceeding. In Supabase Auth, configure the account confirmation email and allowed redirect URLs for the staging domain. Set the sender through Supabase's SMTP settings before production account creation.
3. Create the first administrator account and confirm its email. In the Supabase SQL editor, promote only that known account: `update public.profiles set role = 'admin' where id = (select id from auth.users where lower(email) = lower('OWNER_EMAIL'));`. Verify exactly one row changed. Admin access is checked server-side for every admin API request.
4. Create an Ozow One API client and site for the staging website, and configure a `transaction.complete` webhook subscription in **full** mode pointing to `https://STAGING_DOMAIN/api/payments/ozow-webhook`. Store the client ID, client secret, site code and webhook secret in the server environment. Set `OZOW_ENV=staging` and test a successful payment, cancellation, failure, duplicate delivery, invalid signature, and expired booking before enabling the production client. The webhook signature is verified against the raw body with a five-minute replay window; the return URL never confirms payment.
5. Verify the sending domain in Resend. Add `RESEND_API_KEY` and `EMAIL_FROM`. Schedule an authenticated GET to `/api/internal/notifications` at a short interval with `Authorization: Bearer $CRON_SECRET`; it claims outbox rows safely and retries transient failures up to five times. Add monitoring for messages ending in `failed`.
6. Run the complete flow on staging: customer account and verified email, request, availability, admin unit assignment and amount, agreement review and both signatures, Ozow hosted checkout, webhook-confirmed reservation, invoice and receipt printing, customer email, and duplicate webhook delivery. Keep production rate and cancellation terms in management control until approved.

## Agreement and signing

The agreement is a fixed, versioned document generated from the booking, the supplied `GUEST RULES.pdf`, and management-entered terms. It records the SHA-256 digest, authenticated signer, typed legal name, acceptance text and server timestamp for each party. Management must review and sign the draft first; only then is it emailed to the guest for their signature. Checkout remains unavailable until both parties have signed the same document version. A booking is linked to a customer account only when its email matches that account's confirmed email. The internal workflow is not a claim that a simple e-signature is sufficient for every legal instrument; South Africa's ECT Act distinguishes cases requiring an advanced electronic signature. Get legal advice on the required signature level and agreement wording before using it with guests: [Electronic Communications and Transactions Act 25 of 2002](https://www.gov.za/documents/electronic-communications-and-transactions-act).

The owner supplied six scanned pages of a residential lease template (pages 12-15 and 17-18; page 16 is missing). Those scans were moved out of the public website assets and are stored locally under the Git-ignored `private-documents/lease-template-scans/` folder. The agreement draft adopts the property/room care topics and captures booking-specific dates, price, deposit and cancellation terms. It does not silently import blank fields or long-term fixed lease cancellation, renewal or penalty provisions into an overnight stay. Management must verify its legal identity, per-unit occupancy, deposit/refund handling, cancellation terms, privacy and rental/consumer-law requirements. The draft explicitly requires management/legal review before it is sent or signed.

## Current scope limits

- Business rules for deposits, cancellations/refunds, partial monthly stays, occupancy per room and whether R850 is per room or per bed still require management confirmation. The booking admin enters final amounts manually; no unconfirmed rate formula is assumed.
- The app prepares accommodation invoices and paid receipts. It does not handle tax/VAT registrations or accounting export configuration.
- Email delivery requires the Resend cron to be configured; queued events remain in Postgres if credentials are missing.
- A production domain, Supabase projects, Ozow merchant/site credentials, email sender and reviewed lease terms are not present in the repository. These are deployment inputs, not safe values to invent.
- Do not deploy the booking checkout until the Ozow staging request, full `transaction.complete` signed webhook, payment reconciliation, and real customer account flow have passed with the client's actual merchant configuration. Current Ozow docs require the payment payer `id`; the integration uses the booking reference and checks the full webhook's site code, currency, amount and signed payload. Ozow recommends treating the signed webhook, not the browser redirect, as payment confirmation: [Request Payment](https://hub.ozow.com/api-reference/one-api/post-payments/), [Transaction completed webhook](https://hub.ozow.com/api-reference/one-api/webhooks/transaction-complete/).
