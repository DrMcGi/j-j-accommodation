# Booking platform setup and handoff

The booking system uses Supabase for Postgres and customer authentication, Ozow One API for hosted payments, and Resend for email. Online booking is intentionally unavailable until each provider is configured. The site does not pretend an unpersisted request was saved or a browser return means a payment succeeded.

## Inventory and rates

The migrations seed 9 bachelor units and 4 two-bedroom units, both available for overnight and monthly stays. Each physical room is shared inventory across both stay periods. Availability counts free units per date. Reservation creation rechecks dates in the database, serializes allocation for that room type, assigns one free physical unit, calculates the charge, and holds the room for 20 minutes. An exclusion constraint prevents an active payment hold or confirmed booking from overlapping another booking of the same unit. Expired holds stop reducing availability; confirmed bookings stop reducing availability after their departure date.

The monthly amounts are R7,500 per started month for a bachelor and R13,500 per started month for a two-bedroom. The guest-selected date interval is what gets blocked, with the departure date excluded. Any partial started month is charged at the full monthly rate. Overnight costs R850 per bed per night: one bed for a bachelor (R850/night) and two beds for a two-bedroom (R1,700/night). Those are system pricing rules, not staff-entered quotes. A one-time administrator setup records the legal lessor, occupancy limits, deposit and cancellation policy, and the authorized management signer. New stays then receive a generated agreement with the policy, management authorization and guest-specific details automatically.

## Providers

1. Use a separate Supabase staging project before production. Local development credentials belong in the ignored `.env.local`; deployment credentials belong in the hosting provider's secret settings. Never commit environment files.
2. On a fresh project, apply `supabase/migrations/202611130001_booking_platform.sql`, then `supabase/migrations/202611130002_automatic_room_reservations.sql`, in that order. The existing J & J project already has the base migration from the earlier booking test, so apply only migration `202611130002_automatic_room_reservations.sql` there. For each required migration, open the project in Supabase Dashboard → **SQL Editor → New query**, paste the complete file contents, and click **Run** once. Check the result before continuing; do not rerun a migration after an error without checking what completed. In Supabase Auth, configure account confirmation and allowed redirect URLs for the staging domain. Set the sender through Supabase SMTP or the configured email provider before customer account creation.
3. Create the first administrator account and confirm its email. In the Supabase SQL editor, promote only that known account: `update public.profiles set role = 'admin' where id = (select id from auth.users where lower(email) = lower('OWNER_EMAIL'));`. Verify exactly one row changed. Sign in as that administrator and complete **Admin → Booking setup** once with reviewed legal terms, actual occupancy limits, deposit/cancellation rules, and management authorization. Admin access is checked server-side for every admin API request.
4. Create an Ozow One API client and site for the staging website, and configure a `transaction.complete` webhook subscription in **full** mode pointing to `https://STAGING_DOMAIN/api/payments/ozow-webhook`. Store the client ID, client secret, site code and webhook secret in the server environment. Set `OZOW_ENV=staging` and test a successful payment, cancellation, failure, duplicate delivery, invalid signature, and expired booking before enabling the production client. The webhook signature is verified against the raw body with a five-minute replay window; the return URL never confirms payment.
5. Verify the sending domain in Resend. Add `RESEND_API_KEY`, `EMAIL_FROM` and a strong `CRON_SECRET`. Schedule an authenticated GET to `/api/internal/notifications` at a short interval with `Authorization: Bearer $CRON_SECRET`; it claims outbox rows safely and retries transient failures up to five times. Add monitoring for messages ending in `failed`. After the scheduler is running, set `NOTIFICATIONS_CRON_CONFIGURED=true`; instant reservations stay disabled until then.
6. Run the complete flow on staging: confirmed customer account, live room counts, automatic room assignment and exact price, guest agreement signature, Ozow hosted checkout, webhook-confirmed reservation, invoice and receipt printing, customer email, expiry of unpaid holds, concurrent requests for the last available room, and duplicate webhook delivery. Staff do not review or assign each individual booking.

## Agreement and signing

The agreement is generated from the booking and the one-time administrator-approved policy. It records the SHA-256 digest, guest account, typed legal name, acceptance text and server timestamp. The administrator's authorization to apply the approved standard policy is recorded on each fixed booking agreement; the guest reviews and signs their booking-specific agreement from their account. Checkout stays locked until the guest signature is recorded. A booking is linked to a customer account only when its email matches that account's confirmed email. The internal workflow is not a claim that a simple e-signature is sufficient for every legal instrument; South Africa's ECT Act distinguishes cases requiring an advanced electronic signature. Get legal advice on the required signature level and agreement wording before using it with guests: [Electronic Communications and Transactions Act 25 of 2002](https://www.gov.za/documents/electronic-communications-and-transactions-act).

The owner supplied six scanned pages of a residential lease template (pages 12-15 and 17-18; page 16 is missing). Those scans were moved out of the public website assets and are stored locally under the Git-ignored `private-documents/lease-template-scans/` folder. The agreement draft adopts the property/room care topics and captures booking-specific dates, price, deposit and cancellation terms. It does not silently import blank fields or long-term fixed lease cancellation, renewal or penalty provisions into an overnight stay. Management must verify its legal identity, per-unit occupancy, deposit/refund handling, cancellation terms, privacy and rental/consumer-law requirements. The draft explicitly requires management/legal review before it is sent or signed.

## Current scope limits

- The monthly system charges each started calendar-month anniversary at the full monthly rate; only the guest-selected dates are blocked. Verify this policy with management before customer launch.
- The app prepares accommodation invoices and paid receipts. It does not handle tax/VAT registrations or accounting export configuration.
- Email delivery requires the Resend cron to be configured; queued events remain in Postgres if credentials are missing.
- The Supabase connection is configured locally. The automatic-reservation migration still needs applying to the project. Ozow staging credentials, a public staging domain, verified email sender/cron, and approved one-time booking policy still must be configured before end-to-end online bookings can be enabled.
- Do not deploy the booking checkout until the Ozow staging request, full `transaction.complete` signed webhook, payment reconciliation, and real customer account flow have passed with the client's actual merchant configuration. Current Ozow docs require the payment payer `id`; the integration uses the booking reference and checks the full webhook's site code, currency, amount and signed payload. Ozow recommends treating the signed webhook, not the browser redirect, as payment confirmation: [Request Payment](https://hub.ozow.com/api-reference/one-api/post-payments/), [Transaction completed webhook](https://hub.ozow.com/api-reference/one-api/webhooks/transaction-complete/).
